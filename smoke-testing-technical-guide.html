01｜什麼是冒煙測試？

冒煙測試（Smoke Testing）是一種範圍小、速度快、聚焦核心功能的初步測試。它通常在新版本建置完成、程式部署到測試或正式環境之後立即執行，用來回答一個關鍵問題：

這個版本是否基本可用，值得繼續投入時間做更完整的測試？

名稱源自早期硬體工程：設備第一次通電後，先觀察是否冒煙或發生明顯故障。沒有冒煙不代表設備完全正確，卻代表可以繼續做下一階段檢查。軟體工程借用這個概念，先驗證登入、首頁、資料庫連線、核心 API 等最重要路徑。

冒煙測試也常稱為 Build Verification Test（BVT，建置驗證測試）。它不是要找出所有錯誤，而是攔截會讓整套系統無法繼續測試的重大問題。

02｜冒煙測試的目的與定位

快速阻擋壞版本

若首頁無法開啟、API 全數回傳 500 或資料庫無法連線，就不必繼續執行耗時的完整測試。

降低時間與費用

先跑 3～10 個核心案例，可避免直接執行數百項測試，尤其適合會產生雲端或 AI API 費用的流程。

建立部署信心

確認新版本在目標環境可啟動、設定可讀取、依賴服務可連線，減少「本機正常、上線失敗」。

提供清楚閘門

冒煙測試通過才進入整合、回歸、效能或使用者驗收測試；失敗則立即停止並修復。

03｜和其他測試有什麼不同？

測試類型主要問題範圍／速度常見時機
冒煙測試系統基本上能不能用？窄／快每次建置或部署後
單元測試單一函式或元件是否正確？小／非常快開發與提交程式碼時
整合測試多個模組合作是否正確？中／中等功能整合後
回歸測試修改後是否破壞原有功能？廣／較慢改版、修錯後
健全性測試（Sanity）特定修改是否大致合理？窄且深入／快小幅修改或修補後
驗收測試（UAT）是否符合使用者與業務需求？依情境／較慢正式發布前

實務上，Smoke 與 Sanity 有時會被團隊混用。較常見的區分是：Smoke 檢查整體的關鍵功能是否可運作；Sanity 聚焦某次修改是否合理。

04｜應該測哪些內容？

好的冒煙測試不是隨機挑幾個案例，而是覆蓋系統的「生命線」。常見範圍包括：

  • 應用程式能否啟動，首頁與主要頁面能否開啟。
  • 使用者能否登入、登出，權限是否沒有明顯失效。
  • 最重要的業務流程能否走完，例如建立訂單、送出表單、儲存學習紀錄。
  • 資料庫、檔案儲存、第三方 API 等關鍵依賴能否連線。
  • 正式環境的必要設定是否存在，但不應在輸出中洩漏密鑰。
  • 回應狀態碼、資料結構和基本內容是否符合預期。
判斷原則：如果這項功能壞掉，後續大部分測試是否失去意義？若答案是「是」，它通常應納入冒煙測試。

05｜標準執行流程

1定義核心路徑
2準備環境資料
3執行少量案例
4判定通過／失敗
5放行完整測試
  1. 定義成功條件：每個案例都要有明確輸入、操作、預期結果、逾時與失敗條件。
  2. 準備獨立測試資料：避免使用真實個資；資料應可重建、可清理，並避免案例互相依賴。
  3. 先檢查環境：確認服務網址、模型名稱、資料庫連線與必要環境變數，但只記錄是否存在，不輸出秘密值。
  4. 執行並保留證據：記錄版本、環境、案例編號、時間、狀態碼、延遲與失敗摘要。
  5. 設定硬性閘門：任何關鍵案例失敗，就停止後續完整測試；修復後重新部署並重跑。

06｜網站與 API 實作範例

範例一：使用 Playwright 驗證網站核心流程

import { test, expect } from '@playwright/test';

test('首頁可開啟並進入教材', async ({ page }) => {
  await page.goto(process.env.BASE_URL);
  await expect(page).toHaveTitle(/自然科學|教材/);
  await page.getByRole('link', { name: '開始學習' }).click();
  await expect(page.getByRole('heading', { level: 1 })).toBeVisible();
});

test('學習紀錄可以儲存', async ({ page }) => {
  await page.goto(`${process.env.BASE_URL}/lesson/refraction`);
  await page.getByLabel('我的預測').fill('光線方向會改變');
  await page.getByRole('button', { name: '儲存紀錄' }).click();
  await expect(page.getByText('儲存成功')).toBeVisible();
});

範例二：Shell 檢查 API 健康狀態

#!/usr/bin/env bash
set -euo pipefail

BASE_URL="${BASE_URL:?請設定 BASE_URL}"

curl --fail --silent --show-error \
  --max-time 10 \
  "$BASE_URL/api/health" |
  jq -e '.status == "ok"'

echo "Smoke test passed: API is healthy."

--fail 讓 HTTP 錯誤狀態造成命令失敗，--max-time 避免服務無回應時無限等待，jq -e 則驗證回傳 JSON 的內容，而不只是確認狀態碼。

07｜AI 模型評測的冒煙測試

AI 評測往往牽涉 API 計費、模型延遲與非決定性輸出，因此更適合先跑冒煙測試。例如完整題庫有 40 題，可先挑 5 題，分別涵蓋簡答、推理、格式限制、拒答與較長輸入。

檢查項目最低成功條件失敗時可能原因
API 連線請求成功並在逾時內回覆金鑰、網路、額度或端點錯誤
模型設定指定模型可用模型名稱錯誤、權限不足
結構化輸出JSON 可解析且欄位齊全Schema、提示詞或解析程式問題
評分流程能產生分數與理由評分規準不清或程式映射錯誤
安全記錄日誌不含 API Key 與個資錯誤處理直接印出請求內容

建議的 5 題選樣策略

  • 1 題最簡單、最常見的正常案例。
  • 1 題包含中文字、標點或多行內容。
  • 1 題要求固定 JSON 格式。
  • 1 題接近輸入長度或複雜度上限。
  • 1 題測試錯誤輸入、安全拒答或重試機制。
重要：5 題全部成功，只表示評測管線基本可運作，不代表模型品質已獲充分驗證。品質結論仍需完整題庫、重複試驗與統計分析。

08｜放進 CI/CD 自動執行

冒煙測試最適合部署完成後自動執行。以下 GitHub Actions 範例會對目標網站執行測試；只有通過時，後續完整測試才會開始。

name: Post-deploy smoke test
on:
  workflow_dispatch:
  deployment_status:

jobs:
  smoke:
    if: github.event_name == 'workflow_dispatch' ||
        github.event.deployment_status.state == 'success'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - run: npm ci
      - run: npx playwright install --with-deps chromium
      - run: npm run test:smoke
        env:
          BASE_URL: ${{ secrets.PRODUCTION_URL }}

  full-test:
    needs: smoke
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm test

實務上還可加入 Slack／Email 通知、自動保留螢幕截圖與 trace、失敗時停止流量切換，或在藍綠部署中自動回退至上一個穩定版本。

09｜如何設計好的冒煙案例？

  • 少而關鍵：通常控制在數分鐘內完成；若要跑一小時，已偏離「快速閘門」的定位。
  • 結果穩定：避免依賴隨機資料、外部網站版面或不固定的時間條件。
  • 彼此獨立：任何案例都能單獨重跑，並自行建立與清理資料。
  • 可診斷：失敗訊息應指出哪個步驟、哪個端點、預期與實際結果，而非只顯示「失敗」。
  • 貼近真實：至少包含一條真正的端到端使用路徑，而不只是所有服務各自回傳 200。
  • 持續更新：當核心功能與風險改變，測試清單也必須調整。

通過標準範例

核心案例通過率應為 100%；健康檢查須在 10 秒內完成；端到端路徑須在 60 秒內完成；不接受未分類錯誤；日誌不得含密鑰、個資或完整敏感輸入。

10｜測試失敗時怎麼處理？

  1. 先停止放行：不要在重大故障尚未釐清時繼續跑完整測試或擴大部署。
  2. 確認是否為測試本身不穩：檢查選擇器、測試資料、逾時及第三方依賴。
  3. 收集最小必要證據：版本編號、環境、時間、狀態碼、錯誤摘要與必要截圖。
  4. 依影響分級：服務完全不可用、資料錯誤與安全問題通常列為阻擋發布。
  5. 修復後從頭重跑：不要只人工略過失敗步驟，並確認修復沒有造成新問題。
「重跑就過」不是充分的修復。若案例偶發失敗，應追查不穩定來源；否則團隊久而久之會忽略警報。

11｜可直接使用的冒煙測試檢核表

  • 已標記本次測試的版本、環境、執行者與時間。
  • 應用程式啟動正常，首頁或入口頁可以開啟。
  • 關鍵 API 的狀態碼、回應結構及基本內容正確。
  • 登入與必要權限正常，未登入者不能存取受保護內容。
  • 最重要的一條端到端使用流程可以完成。
  • 資料庫、儲存服務與必要第三方服務可以連線。
  • 錯誤訊息可理解，且不洩漏密鑰、個資與內部堆疊資訊。
  • 測試資料可以安全建立與清除，不污染正式資料。
  • 所有核心案例 100% 通過後，才啟動完整測試。
  • 失敗時已有停止、通知、回退與重新測試機制。

12｜常見問題與迷思

冒煙測試通過，就代表系統沒有 Bug 嗎？

不是。它只證明最基本、最關鍵的功能在當下環境可運作，無法取代完整的功能、回歸、效能、安全與驗收測試。

應該全部自動化嗎？

高頻、穩定、容易判定的案例應優先自動化。介面仍在快速變動或需主觀判斷時，可暫時保留人工檢查，但應有固定腳本和紀錄。

每次部署都要執行嗎？

建議如此，特別是正式環境。即使程式碼沒有改到核心功能，部署設定、環境變數、資料庫遷移或依賴服務仍可能造成問題。

多少個案例最合適？

沒有固定數量。以覆蓋所有生命線且能在數分鐘內完成為原則。小型教材網站可能 3～8 個，大型平台可能數十個，但都應維持快速與穩定。

能直接對正式環境測試嗎？

可以，但必須使用專用測試帳號、可識別且可清理的資料，避免觸發真實付款、寄信或不可逆操作。高風險動作宜用沙盒或替代端點。

結語｜先確認「能跑」，再證明「跑得對」

冒煙測試的價值，在於用很小的成本提早發現很大的問題。它建立了一個清楚節奏：部署 → 快速驗證 → 通過閘門 → 完整測試 → 正式放行。對網站、互動教材、後端 API 或 AI 評測系統而言，這道第一關都能有效減少無效等待、雲端費用與上線風險。

最重要的觀念是：冒煙測試不是完整品質保證，而是一個快速可信的「繼續／停止」判斷機制。
