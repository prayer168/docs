摘要

在 Codex 中，最昂貴的錯誤通常不是「選錯模型」，而是把高階模型與高推理強度設成長時間的常駐預設。當工作本身只是格式調整、局部修正、一般程式撰寫或可明確拆解的工程任務時，使用 GPT-5.6 Sol High 往往會投入超過必要的推理預算。

本指南提出一套「分層路由」方法：Luna 處理範圍明確且高頻的工作，Terra 作為日常程式開發主力，Sol 處理需要判斷、跨檔案理解與架構決策的工作，而 Astra 或極高推理設定只留給高難度、品質優先且確實需要更多探索的任務。核心原則是：先使用能達到品質門檻的最輕設定，只有在證據顯示品質不足時才升級。

本文同時區分「Codex 產品中的使用量／credits」與「OpenAI API 的逐 Token 計價」。API 公開價格可用來理解不同模型的相對成本級距，但不能直接推算 Codex 方案中的使用額度消耗。

一句話結論：日常預設以 Terra Medium 為中心；小事降到 Luna／Terra Low；架構與審查升到 Sol Medium；Sol High／xhigh／max 或 Astra 只在真正卡關時使用。

1. 為什麼 Sol High 很容易「一下就燒掉很多額度」？

推理模型在輸出最終答案之前，會使用內部 reasoning tokens 進行規劃、檢查替代方案、工具使用與錯誤修復。推理強度從 low、medium 提升到 high、xhigh 或 max，本質上是在允許模型投入更多推理工作。這可能提升困難任務的可靠度，但在簡單任務上也可能形成過度運算。

Codex 又不是單次問答工具，而是 Agent。一次「修好這個 bug」可能包含讀檔、搜尋、修改、執行測試、讀取錯誤、再次修改、再次驗證等多個循環。若每一輪都由高成本模型以高推理強度執行，使用量會快速累積。

此外，工作範圍也直接影響成本。掃描整個 repository、攜帶非常長的上下文、反覆載入大型檔案，以及要求「全部檢查、全部修正、全部重構」，都會顯著增加模型需要處理的資訊量。

4. 最實用的「四檔模式」

第 1 檔｜Luna Low雜工模式：文字、格式、命名、重複性修改、清楚的小任務。目標是快、便宜、做完即停。
第 2 檔｜Terra Low／Medium日常工程模式：一般程式撰寫、ESP32、Python Gateway、API、測試與常規除錯。建議成為多數 Codex 任務的預設。
第 3 檔｜Sol Medium專業判斷模式：跨檔案理解、架構規劃、重要 refactor、review、完整性要求較高的工程任務。
第 4 檔｜Sol High 以上／Astra專家會診模式：多次失敗仍無法定位、複雜 concurrency、重大遷移、安全性或高風險決策。問題解完後立刻降檔。

5. 比「選模型」更重要的 6 個省用量策略

  1. 限制工作範圍。不要說「檢查整個專案」。改成「只檢查 /gateway；最多找 3 個直接相關問題；不要修改其他資料夾」。
  2. Plan 與 Execute 分開。先讓 Sol Medium 只做 root cause 與修復計畫；確認方向後，把大量實作交給 Terra Medium。避免高階模型從頭做到尾。
  3. 採用 Minimum Necessary Change。明確要求不要做無關 refactor、不要擴大範圍、修改後只執行相關測試。
  4. 測試通過即停止。Agent 容易在完成後繼續「順便改善」。加上 stop condition：相關測試通過且需求滿足後停止，不再延伸。
  5. 高階模型只做 Quality Gate。架構規劃、review、疑難診斷使用 Sol；大量 coding、修檔、測試交給 Terra／Luna。
  6. 難題結束立即降檔。高推理設定很容易被忘在模型選擇器中。解完難題後，下一個任務前先確認是否已切回日常檔位。

6. 推薦的 Codex 工作流：高階模型做腦，大量實作交給均衡模型

① 分析Sol Medium
② 實作Terra Medium
③ 整理Luna／Terra
④ 審查Sol Medium
⑤ 救火Sol High／Astra

這個流程的重點不是追求「最強模型從頭包到尾」，而是把昂貴的推理集中在最需要判斷的節點。真正耗時但規格明確的工作，通常可以交給更便宜的模型完成。

8. 可直接貼進 Codex 的「節省用量工作規則」

工作原則：
1. 優先採用 minimum necessary change。
2. 不要掃描整個 repository，除非目前證據不足。
3. 先讀取與問題直接相關的檔案。
4. 不做與任務無關的 refactor。
5. 先定位 root cause，再進行修改。
6. 修改後只執行與本次變更直接相關的測試。
7. 若測試通過且需求已滿足，立即停止，不延伸改善。
8. 若需要擴大工作範圍，先說明原因與預計新增讀取的區域。

9. 決策樹：每次工作前只問 4 個問題

  1. Q1：任務是否範圍明確、答案近乎機械式？
    是 → Luna Low；否 → Q2
  2. Q2：主要工作是不是一般 coding、測試、API、腳本或常規除錯？
    是 → Terra Low／Medium；否 → Q3
  3. Q3：是否需要跨檔案理解、架構判斷、審查或高完整度？
    是 → Sol Medium；否 → 回 Terra Medium
  4. Q4：Sol Medium 已失敗、問題高度複雜或風險極高嗎？
    是 → Sol High／更高推理或 Astra；完成後立即降檔

10. 關於 API Token 價格與 Codex 額度：不要混為一談

OpenAI API 會公布模型每百萬輸入／輸出 Token 的價格，因此可清楚看到模型之間的成本級距。例如，官方文件顯示 GPT-5.6 Luna 明顯偏向成本敏感、高流量工作，而 GPT-5.6 Sol 是旗艦級模型。這些數字能幫助理解「相對成本」，但 ChatGPT Codex 的方案額度、credits、速率限制與產品內部計量方式可能另有規則。

因此，若你在 Codex 介面看到「額度很快下降」，不應簡化成「可見輸出 Token × API 單價」。實際耗用還可能與模型、推理強度、輸入上下文、Agent 多步循環、工具呼叫與產品方案規則有關。最可靠的優化方法，是縮小任務範圍、降低不必要的推理強度，並建立模型分流制度。

如果希望更制度化，可以把這套規則直接寫入專案 AGENTS.md 或開發規範中，讓「什麼任務用什麼模型」成為工程流程的一部分，而不是每次臨時憑感覺選擇。

結論

節省 Codex 用量的核心，不是永遠選最便宜的模型，而是建立「任務難度、模型能力、推理強度」三者之間的匹配。高階模型的價值在於處理高價值判斷，而不是承包所有低風險工作。
