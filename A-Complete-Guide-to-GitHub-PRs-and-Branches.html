一、先用一句話理解 Branch 與 PR

這兩個名詞常一起出現，但負責的工作不同。Branch 是「修改發生在哪裡」，PR 是「如何把修改送交檢查並申請合併」。

Branch（分支）

從既有版本分出一條獨立工作路線，讓你新增功能、修正錯誤或做實驗時，不會立刻影響正式版本。

PR（Pull Request）

把某個分支中的修改提出來，讓自己或團隊查看差異、留言、測試與審查，再決定是否合併到目標分支。

核心記憶：Branch 是「獨立草稿」，PR 是「送審申請」，Merge 是「正式採用」。

二、Branch（分支）到底是什麼？

在 GitHub 專案中，Branch 是一條獨立的開發路線。你通常會從目前穩定的預設分支建立新分支，再於新分支完成某一項明確任務。

用「正式教材與修改草稿」來比喻

假設你有一套正在提供學生使用的「光的折射互動教材」，正式網站位於 main。現在你想新增硬幣雙重影像實驗，但功能尚未完成，若直接在 main 修改，可能讓正式網站在開發途中出錯。

更安全的做法是建立：

分支名稱範例
feature/add-coin-experiment

你可以在這條分支中修改 HTML、CSS 與 JavaScript，等測試完成後，再透過 PR 申請合併回 main。

Branch 的四個主要價值

隔離風險

尚未完成的修改不會立即污染正式版本。

平行工作

多人可同時處理不同功能或修正。

容易比較

GitHub 能清楚顯示分支之間的差異。

方便放棄

實驗失敗時可刪除分支，不必破壞 main。

常見的分支命名方式

分支名稱用途範例情境
main正式、穩定版本目前正在部署的教材網站
develop整合中的開發版本大型團隊先整合功能，再進 main
feature/add-quiz新增功能加入互動測驗
fix/mobile-layout修正錯誤解決手機版橫向捲軸
docs/update-readme更新文件修改 README 操作說明
release/v2.0準備發布版本整理 2.0 正式發布內容

三、Git 技術上如何表示 Branch？

從使用者角度看，Branch 很像「複製一份專案」；但從 Git 的內部結構來看，分支其實是一個指向某次 Commit 的輕量可移動指標。

重要觀念：建立 Branch 通常不會真的複製整個資料夾。它只是先指向與原分支相同的 Commit；當新分支產生新的 Commit 後，兩條歷史才開始分開。
概念模型
A ← B ← C
        ↑
       main

# 建立 feature 分支時，兩個名稱先指向同一個 Commit C
A ← B ← C
        ↑
       main
        ↑
      feature

# 在 feature 新增 Commit D 後
A ← B ← C ← D
        ↑     ↑
       main  feature

HEAD 又是什麼？

HEAD 通常表示你目前正在工作的分支或 Commit。當你執行 git switch feature/add-quiz，HEAD 就會移到該分支。接下來建立的新 Commit，也會接在這個分支目前指向的 Commit 後面。

四、PR（Pull Request）是什麼？

Pull Request 是「提出一組修改，請求審查與合併」的協作機制。它不是單純上傳檔案，也不是立即合併，而是一個把修改內容、討論、測試、審查與合併決策集中在同一頁面的工作空間。

建立 PR ≠ 已經合併。PR 可以被留言、要求修改、暫時保留、關閉，或在條件符合後才合併。

Base 與 Compare／Head

Base branch

修改要進入的「目標分支」，常見為 main。

Compare／Head branch

包含新修改的「來源分支」，例如 feature/add-quiz。

PR 方向
base: main  ←  compare: feature/add-quiz

意思：把 feature/add-quiz 的修改，申請合併到 main。

為什麼名稱叫 Pull Request？

它的概念不是「請下載我的檔案」，而是「我已經完成一組變更，請專案維護者檢查，並考慮把這些變更拉入目標分支」。因此 PR 的核心是提案、審查與合併。

五、從建立分支到完成 PR 的完整流程

以下以「為互動教材新增硬幣實驗」為例，展示在本機 Git 與 GitHub 網站上的完整操作。

步驟 1：回到 main 並取得最新內容

Terminal
git switch main
git pull origin main

先確保新分支建立在最新的正式版本上，可減少日後衝突。

步驟 2：建立並切換到功能分支

Terminal
git switch -c feature/add-coin-experiment

-c 表示建立新分支並立即切換過去。

步驟 3：修改並查看差異

Terminal
git status
git diff

git status 查看哪些檔案有變更；git diff 查看尚未加入暫存區的內容差異。

步驟 4：建立 Commit

Terminal
git add .
git commit -m "新增硬幣雙重影像互動實驗"

Commit 是有說明文字的版本節點。訊息應描述「這次完成什麼」，避免只寫 update 或 fix。

步驟 5：Push 到 GitHub

Terminal
git push -u origin feature/add-coin-experiment

-u 會設定追蹤關係，之後在同一分支通常只需執行 git push。

步驟 6：在 GitHub 建立 PR

開啟 Repository 後，GitHub 常會顯示 Compare & pull request。確認來源與目標分支、填寫標題與說明，再按下 Create pull request。

PR 說明範本
## 修改內容
- 新增硬幣雙重影像模擬
- 加入水位控制滑桿
- 顯示兩條可能光路
- 修正手機版按鈕尺寸

## 測試環境
- Windows Chrome：正常
- Android Chrome：正常
- iPad Safari：正常

## 注意事項
- 尚未加入學習紀錄匯出功能

步驟 7：回應審查並繼續 Push

若審查者要求調整，你仍在同一個來源分支修改、Commit、Push；GitHub 會自動把新的 Commit 加入原本 PR，不必重新開 PR。

Terminal
git add .
git commit -m "調整手機版實驗按鈕與文字間距"
git push

步驟 8：Merge 並刪除功能分支

確認測試、審查與衝突狀態均可接受後，按下合併按鈕。合併成功後可刪除功能分支；已經合併進 main 的內容不會因此消失。

六、PR 頁面裡可以檢查什麼？

Conversation

PR 說明、討論、審查結果、自動化狀態與事件時間軸。

Commits

這條 PR 分支依時間建立的全部 Commit。

Files changed

新增、刪除與修改的程式碼差異，也是人工審查重點。

Checks

GitHub Actions、建置、測試、格式或安全掃描結果。

常見 Review 結果

Comment
留下意見，但不明確表示同意或反對合併。
Approve
審查者認為目前修改可接受，同意合併。
Request changes
審查者要求先修改特定問題，再重新送審。

審查 AI Agent 產生的 PR 時，至少看這些

  • AI 是否修改了任務範圍以外的檔案。
  • 是否刪除了原本功能、資料或設定。
  • HTML 是否仍有正確語意與無障礙標籤。
  • 手機、平板、桌機版面是否正常。
  • 是否新增外部追蹤碼、陌生套件或敏感資訊。
  • 自動化測試通過，是否真的代表使用流程正常。

七、PR 的三種常見合併方式

Create a merge commit

保留來源分支的完整 Commit，並額外建立一個 Merge Commit，能清楚看到功能分支何時被整合。

適合：想保留完整分支脈絡的團隊。

Squash and merge

把來源分支中的多個零碎 Commit 壓成一個 Commit，再放入目標分支，讓 main 的歷史較乾淨。

適合：個人網站、小型教材專案、AI 多次修正。

Rebase and merge

把來源分支 Commit 依序接到目標分支最新歷史後面，不建立額外 Merge Commit，形成較直線的紀錄。

適合：重視線性歷史且熟悉 Git 的團隊。

初學者建議：個人 GitHub Pages 或數位教材專案，可優先考慮 Squash and merge，讓正式分支只留下每項功能的一筆清楚紀錄。

八、什麼是 Merge Conflict（合併衝突）？

當兩條分支修改同一個檔案中的相同位置，而 Git 無法安全判斷該保留哪一個版本時，就會發生 Merge Conflict。

衝突標記範例
<<<<<<< HEAD
<h1>光的折射互動實驗室</h1>
=======
<h1>神奇的光線探索</h1>
>>>>>>> feature/new-title

你必須人工判斷最後要保留哪個版本，或整合成新的內容：

解決後
<h1>神奇的光線折射互動實驗室</h1>

降低衝突的做法

  • 建立分支前，先更新最新的 main。
  • 功能分支不要存活太久，完成後盡快開 PR。
  • 每個分支只處理一個明確任務，避免大範圍重寫。
  • 多人協作時，先分配檔案或功能範圍。
  • PR 開啟期間，定期同步目標分支的最新變更。

十、只有一個人開發，也需要 Branch 與 PR 嗎？

不一定是強制的，但非常值得。對 GitHub Pages、教學網站或使用 AI Coding Agent 的專案，PR 可以成為「正式上線前的檢查站」。

直接改 main

  • 操作步驟少
  • 適合極小修正
  • 改壞後可能立即影響正式網站
  • 不容易在合併前集中檢查差異

Branch ＋ PR

  • 正式網站較安全
  • 可先看 Files changed
  • 可執行自動測試與預覽
  • 留下清楚的修改理由與歷史

推薦的 AI Agent 安全流程

人類描述任務
AI 建 Branch
AI 修改與測試
AI Commit
AI 開 Draft PR
人類 Review
確認後 Merge
不建議：讓 AI Agent 在沒有檢查差異、沒有測試、沒有備份的情況下，直接強制推送或覆寫 main。

十一、如何把這篇網頁發布到 GitHub Pages？

這份文章是單一 index.html，不需要安裝套件或執行建置工具。把檔案上傳到 Repository 後，即可設定 GitHub Pages 從指定分支的根目錄或 /docs 資料夾發布。

方法 A：直接從 main 根目錄發布

  1. 建立一個新的 GitHub Repository。
  2. 把本檔命名為 index.html 並放在 Repository 根目錄。
  3. 進入 Settings → Pages。
  4. 在 Build and deployment 選擇 Deploy from a branch。
  5. Branch 選擇 main，Folder 選擇 /(root)。
  6. 儲存後等待 GitHub Pages 完成發布。

方法 B：從 main 的 /docs 資料夾發布

若 Repository 同時包含其他程式碼，可把網站檔案放在：

Repository 結構
your-repository/
├── README.md
├── src/
└── docs/
    └── index.html

接著在 Pages 設定中選擇 main 與 /docs。

建議先用分支測試網站更新

更新本文的安全流程
git switch main
git pull
git switch -c docs/update-pr-branch-article
# 修改 index.html
git add index.html
git commit -m "更新 PR 與 Branch 技術文章"
git push -u origin docs/update-pr-branch-article
# 到 GitHub 開 PR，確認後再 Merge
發布提醒：不要把 API Key、密碼、學生個資或私人資料寫進前端 HTML。GitHub Pages 發布後，瀏覽器能下載的內容原則上都應視為公開。

十三、常見問題

建立 Branch 後，一定要建立 PR 嗎？

不一定。分支可以只用於個人實驗或暫存工作；但若要把修改整合進正式分支，使用 PR 通常更容易檢查、討論與留下紀錄。

建立 PR 後，還可以繼續修改嗎？

可以。只要繼續把 Commit Push 到同一個來源分支，PR 內容通常會自動更新。

Close PR 和 Merge PR 一樣嗎？

不一樣。Close 表示關閉提案但不合併；Merge 表示接受修改並整合到目標分支。

刪除已合併的 Branch，會刪掉正式內容嗎？

通常不會。功能分支的 Commit 已經整合到目標分支後，刪除來源分支只是移除該分支名稱與指標。

Pull Request 和 git pull 是同一件事嗎？

不是。Pull Request 是 GitHub 的協作與合併提案；git pull 是把遠端更新抓到本機並整合的 Git 指令。

可以從 main 對 main 建立 PR 嗎？

PR 需要比較不同的來源與目標分支；同一個分支沒有可提議合併的差異。
